# Authentication & Identity Architecture: Catalyst

This document defines the multi-role identity framework, onboarding sequences, state management structures, and security configurations planned for Catalyst.

---

## 1. Multi-Tenant User Roles & Data Models

Catalyst manages four distinct user categories. Each role initializes a specific schema and workspace configuration:

### 1.1 Student (Candidate)
- **Purpose**: Academic-to-industry employability tracking.
- **Scope**: Accesses portfolio designers, internship application hubs, and mentor booking timelines.
- **Data Model Parameters**:
  - `profile`: { name, email, avatarUrl, bio, linkedinUrl, githubUrl }
  - `education`: { institution, degree, major, level, graduationYear }
  - `competencies`: { skills: string[], certificates: string[], assessmentScores: number[] }
  - `internships`: { applicationsCount: number, activePlacements: string[] }
  - `mentorship`: { bookedSessionsCount: number, feedbackNotes: string[] }

### 1.2 Mentor (Advisor)
- **Purpose**: Academic and industry guidance.
- **Scope**: Manages consultation calendars, views candidate portfolios, and writes feedback reports.
- **Data Model Parameters**:
  - `profile`: { name, email, avatarUrl, bio, company, title }
  - `expertise`: { fieldCategories: string[], targetSkills: string[] }
  - `scheduling`: { availableDays: string[], activeSlots: string[] }
  - `mentorshipHistory`: { sessionsCompleted: number, activeMentees: string[] }

### 1.3 Employer (Recruiter)
- **Purpose**: Recruitment and industry engagement.
- **Scope**: Creates job postings, manages applicants pipelines, and coordinates interview steps.
- **Data Model Parameters**:
  - `companyInfo`: { name, website, scale, location, logoUrl, desc }
  - `sector`: { industryTypes: string[], techStackFocus: string[] }
  - `postings`: { activeJobsCount: number, jobOpenings: string[] }
  - `candidates`: { screeningQueue: string[] }

### 1.4 Admin (Moderator)
- **Purpose**: Platform governance and oversight.
- **Scope**: Approves employer registrations, audits flagged postings, and monitors analytics.
- **Data Model Parameters**:
  - `auditLogs`: { actionHistory: string[] }
  - `approvals`: { pendingEmployers: string[], flaggedReports: string[] }

## 2. Authentication Journey Design

The lifecycle of an account follows a strict unidirectional wizard stepper sequence:

```
[ New Visitor ] 
      │
      ▼
[ Registration Page ] ( /register - Single Entry Point )
      │
      ▼
[ Role Selection ] ( Student ─ Mentor ─ Employer )
      │
      ▼
[ Onboarding Wizard Stepper ] ( 3-4 Steps of profile compilation )
      │
      ▼
[ Dashboard Landing ] ( Configured for the active user role )
```

---

## 3. Registration Strategy

- **Endpoint**: `/register`
- **Design Parameters**:
  - A single input portal containing: Name, Email, Password, and Password Confirmation.
  - Upon submission validation success, the system creates a base user account and routes them directly to the **Role Selection Toggler** screen.
  - *Note*: Administrator profiles cannot be registered publicly. They must be manually generated by the system seeds or created by existing system administrators.

---

## 4. Login Strategy

- **Endpoint**: `/login`
- **Design Parameters**:
  - Email/Password form.
  - Interactive features:
    - `Remember Session` (Stores auth state in persistent cookies / localStorage).
    - `Password Recovery` (Redirects to a mock recovery email dispatch wizard).

---

## 5. Role-Based Onboarding Steppers

Onboarding requires separate wizards to populate role schemas before database insertion:

### 5.1 Student Wizard Steps
- **Step 1: Basic Information** — Personal summary, links (GitHub, LinkedIn).
- **Step 2: Academic Background** — Degree, major, current level (e.g. 400).
- **Step 3: Skills & Interests** — Self-assessment sliders, target tech stacks.
- **Step 4: Career Goals** — Preferred industry roles (e.g. Frontend Dev, Cloud Engineer).

### 5.2 Mentor Wizard Steps
- **Step 1: Professional Profile** — Job title, company name, summary.
- **Step 2: Areas of Expertise** — Target fields list, bio detail notes.
- **Step 3: Availability** — Choice of days and scheduling constraints.

### 5.3 Employer Wizard Steps
- **Step 1: Company Details** — Corporate name, registration number, scale.
- **Step 2: Industry Sector** — Core focus domains, tech stack requirements.
- **Step 3: Verification Credentials** — Document uploads (verified via administrator review).

---

## 6. Security Considerations

- **Password Rules**: Minimum 8 characters, requiring at least one number and one special character (validated via Zod schemas).
- **Zod Data Verification**: Client-side validation checks on all fields before service execution.
- **Protected Layout Wrappers**: Layout check on Next.js routing groups. Accessing `/dashboard/student/*` checks if user session role is `student`. If not, redirects to `/login`.
- **Session Caching**: Session stored inside a Zustand Auth Store, synced with secure cookies/localStorage for persistent logouts/sessions.
